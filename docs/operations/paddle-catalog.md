# Paddle catalog operations

This runbook is limited to the D09/F10 Paddle catalog. It does not change UI,
legal documents, or user entitlements.

## Safety model

- `infra/paddle/catalog-d09-v1.json` is the versioned desired state. It contains
  no Paddle IDs or credentials.
- Product and price IDs are accepted only from Paddle API responses. The
  provisioner never fabricates them.
- The provisioner is read-only unless `--apply` is passed. It only creates
  resources carrying the exact `d09-v1` Postqron markers and never edits or
  archives unmarked or legacy resources.
- API keys, webhook secrets, and the resolved runtime mapping live in the
  selected GitHub Environment. They must never be copied to logs, commits, PR
  text, or issue comments.
- Paddle sandbox uses the `staging` GitHub Environment; Paddle production uses
  the `production` GitHub Environment. They use separate Paddle accounts, keys,
  webhook destinations, and generated IDs.

Paddle products cannot be deleted and old prices must be archived rather than
deleted. The D09 cutover therefore changes the runtime mapping used for new
checkout composition; it does not rewrite existing subscriptions.

## Secret-store prerequisites

Create the `staging` and `production` GitHub Environments and protect
`production` with a required reviewer. Configure these secrets from the
organization's secret manager using stdin, never command-line values:

- `PADDLE_API_KEY`: a current-format key scoped to product/price read and write
  for plan/apply, or read for verify;
- `PADDLE_WEBHOOK_SECRET`: the secret of that environment's notification
  destination;
- `PADDLE_CATALOG_JSON`: the 14-entry mapping generated by a successful apply.

The environment/key pairing is validated (`pdl_sdbx_…` for `sandbox`,
`pdl_live_…` for `production`). A production key is rejected in sandbox and
vice versa.

Example secret-store transfer, where each source file is supplied directly by
the approved secret manager and kept outside the repository:

```sh
gh secret set PADDLE_API_KEY \
  --env staging --repo apdsoftware/postqron < /secure/path/paddle-sandbox-api-key
gh secret set PADDLE_WEBHOOK_SECRET \
  --env staging --repo apdsoftware/postqron < /secure/path/paddle-sandbox-webhook-secret
```

Repeat for `production` only after the sandbox gate below passes. Do not use
`echo`, shell tracing, or a command-line argument containing a secret.

## Sandbox gate

Run the manual `Paddle catalog` workflow in this order:

1. `sandbox` / `plan` / `d09-v1`. This inventories only and must show either
   `create` or `reuse` for exactly 3 products and 14 prices.
2. Review the plan. `Start` must be absent. Pro has maximum quantity 6, Team
   maximum quantity 9, and Unlimited is flat with quantity exactly 1.
3. `sandbox` / `apply` / `d09-v1`. Re-running apply must report only `reuse`.
4. Download the seven-day mapping artifact and store it without modification:

   ```sh
   gh run download RUN_ID \
     --repo apdsoftware/postqron \
     --name paddle-catalog-sandbox-d09-v1 \
     --dir /secure/path/paddle-sandbox-mapping
   gh secret set PADDLE_CATALOG_JSON \
     --env staging --repo apdsoftware/postqron \
     < /secure/path/paddle-sandbox-mapping/paddle-catalog-mapping.json
   ```

5. Run `sandbox` / `verify` / `d09-v1`. The read-only check validates product
   IDs, active status, EUR amounts, monthly/annual billing cycles,
   `tax_mode=location`, no Paddle trial, and exact quantity bounds.
6. Against a non-personal sandbox workspace, verify monthly and annual checkout
   for Pro quantities 1 and 6, Team quantities 1 and 9, and flat Unlimited.
   Record Paddle transaction/subscription IDs only in the restricted operations
   record, not in the PR.
7. Verify renewal simulation, Pro↔Team↔Unlimited upgrade/downgrade previews,
   failed-payment behavior, and a signed webhook. Entitlement must change only
   after the verified webhook; Unlimited must always contain one price item
   with quantity 1.

Attach only workflow/run IDs, pass/fail status, catalog version, environment,
and redacted screenshots to the issue/PR. Never attach tokens, webhook
signatures, request bodies containing personal data, or secret values.

## Production gate

Production apply is permitted only when all sandbox steps pass, the production
GitHub Environment requires approval, the commercial Paddle account permits
the sub-€10 prices required by D07, and the release coordinator confirms that
#176–#179 will be released coherently.

Run `production` / `plan`, review it independently, then approve and run
`production` / `apply`. Store the generated production mapping in the
production `PADDLE_CATALOG_JSON` secret and run `production` / `verify`.
Sandbox and production IDs must differ for every product and price.

Do not enable the D09 mapping in the application runtime or expose the new
checkout until dependent UI/legal release gates are complete.

## Legacy prices, cutover, and rollback

Before production cutover, inventory every legacy price ID and all active,
trialing, paused, or past-due subscriptions that reference it. Any missing or
ambiguous subscription blocks retirement.

- New checkout uses only the `d09-v1` mapping after cutover.
- Legacy price IDs are retained solely for existing-subscription migration and
  are never added to the D09 mapping.
- After the final subscription is migrated and reconciled, archive the exact
  inventoried legacy price IDs through a separately reviewed, environment-
  protected operation. Never discover-and-archive by name or wildcard.
- Keep the inventory and pre-cutover mapping in the restricted operations
  record for billing support and rollback.

Rollback before any D09 purchase means restoring the previous protected runtime
mapping and archiving only the exact newly generated D09 price IDs. After any
D09 purchase, do not blindly restore or archive: freeze new checkout, reconcile
affected subscriptions and transactions, then execute an approved migration
plan. Existing financial records are never deleted.
